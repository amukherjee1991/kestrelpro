# KestrelPro design

How KestrelPro is put together and why. For using it, see the [README](../README.md).

## Pieces

```
            clients ── DNS :53 ──┐
                                 ▼
 ┌──────────── kestrelpro container (Alpine, from docker-pi-hole) ────────────┐
 │ start.sh                                                                     │
 │  ├─ pihole-FTL  (unmodified upstream release, pinned by checksum)            │
 │  │     DNS, block lists, REST API, admin UI (web fork) on :80                │
 │  └─ kestrel-engine (Python, supervised, lower priority, OOM-killed first)    │
 │        follows the query log → queue → model → policy → deny/allow lists     │
 │        SQLite in /etc/kestrel; API on :8090 for the KestrelPro pages          │
 └────────────────────────────────────────────┬─────────────────────────────────┘
                                              │ HTTP
                                    ┌─────────▼─────────┐
                                    │ Ollama (any host) │  GPU optional
                                    └───────────────────┘
```

- **DNS never depends on the engine.** FTL starts first and never waits for it. If the engine
  stops, blocking continues and only AI review pauses. `KESTREL_ENGINE=off` runs DNS only.
- **The engine is a separate process**, not part of FTL. It talks to FTL over its REST API
  with FTL's local CLI password, which can manage lists but not change settings.
- **Ollama stays a separate service**, bundled in the compose file or anywhere on the network.
  A model server doesn't belong inside a DNS server's image.

## Forks

| Upstream | Forked? | Why |
|---|---|---|
| `pi-hole/FTL` | No | Everything needed is reachable through its API and config. A C fork would mean rebasing a dnsmasq fork on every security release. |
| `pi-hole/pi-hole` (core) | No | Pinned tag. |
| `pi-hole/web` | Yes | The KestrelPro pages, a modern skin and debranding, as a short patch series. |
| `pi-hole/docker-pi-hole` | Yes | Pins FTL by checksum, builds from the forks, supervises the engine. |

The web fork keeps changes small to rebase cleanly: new pages are new files; upstream files get
only marked hooks (`kestrelpro:begin` / `kestrelpro:end`): the sidebar, the query log, one
stylesheet line. Debranding is generated by `tools/debrand.sh` as the top commit of each
branch and checked by `tools/check-branding.sh`. `UPSTREAM.json` records the pinned releases; a
weekly workflow opens an issue when upstream publishes newer ones.

## How a domain is judged

1. The engine reads new queries by ID every few seconds (paging past FTL's 10,000-row limit).
2. Allowed domains not seen before (or whose verdict expired) are queued; local names, the
   never-block list and allow-listed domains are skipped.
3. Batches go to the model with local evidence (devices, rhythm, lookups next to blocked ones)
   and, optionally, a few of the user's own past decisions as examples.
4. Each device's groups decide what happens: Review first queues it, Automatic blocks it for
   those groups only (on a 24 h trial), Off ignores it.
5. Everything is recorded with the model, its exact digest and the prompt version, so the
   Accuracy page can grade models and prompts against the user's decisions.

The first lookup of a new domain is always answered; blocking follows within seconds. Holding
DNS answers for a model's decision would need a patched FTL and would add seconds to lookups.

## Security model

- One login: the admin UI's. The engine checks the browser's `sid` cookie with FTL (cached
  10 s); changes also need that session's CSRF token. A password-less admin UI counts as
  signed out.
- CORS only for the admin UI's own host (or configured origins), never `*`.
- The engine's own FTL session can't change FTL's configuration.
- Nothing is sent outside the network unless the user sets up a notification address.

## Licensing and names

- Everything derived from Pi-hole is EUPL-1.2. Distributing it means publishing the source
  of each build, keeping notices, and marking changes (`KESTRELPRO-CHANGES.md` in each fork).
- Pi-hole's trademark rules forbid redistributing the software with its marks, so the admin
  UI is debranded; the About page states the origin.
- Internal identifiers (`pihole-FTL`, `/etc/pihole`, `FTLCONF_*`) are unchanged for
  compatibility. Confirm with Pi-hole LLC that this is acceptable before publishing images.
- Model weights aren't bundled; they're pulled on first use under their own licences.
